CONTEXT
GuitarTap is a guitar tap tone analysis app built in SwiftUI targeting iOS, iPadOS, and macOS. The app captures audio via the microphone, performs FFT-based frequency analysis, detects and averages tap tone events, and displays results in an interactive frequency response chart. The chart supports pan, zoom, draggable peak annotations, and a crosshair tracking cursor. The codebase has a SwiftUI/Swift implementation.
TASK
Analyze the GuitarTap codebase and produce a comprehensive test plan covering both automated and interactive (manual) tests. Then implement the automated tests.

PART 1 — TEST PLAN
Produce a structured test plan document covering the following areas. For each test, specify: test name, type (unit / integration / UI / manual), target platforms (iOS / iPadOS / macOS), priority (high / medium / low), and a one-line description.
Areas to cover:

FFT Pipeline — windowed FFT, parabolic interpolation for peak frequency refinement, frequency bin accuracy, edge cases (silence, clipping, pure tones)
Tap Trigger Detection — onset detection logic, threshold behavior, rejection of noise and false triggers, minimum inter-tap interval enforcement
Averaging — accumulation of tap events, running average correctness, outlier rejection if present, reset behavior
Audio Stack — AVAudioSession configuration, microphone permission states, session interruption and resumption (phone call, other app), input format handling
Chart Interaction State — pan offset, zoom scale, crosshair position as view model state transitions driven by gesture input values (not gesture simulation)
Draggable Peak Annotations — annotation position state, drag start/end, snap or clamp behavior, undo if present
Cross-Platform UI — presence and accessibility of key controls on all 3 targets, layout correctness at relevant window sizes
Regression Smoke Tests — app launches without crash, chart renders with synthetic data, recording session starts and stops cleanly

For interactive/manual tests, include: preconditions, step-by-step procedure, and expected result.

PART 2 — AUTOMATED TEST IMPLEMENTATION PLAN
For each automated test identified in Part 1, produce an implementation plan:

Identify which source files and types are directly under test
Identify what needs to be refactored or extracted to make the code testable (e.g., view model extraction, protocol abstraction for audio session, dependency injection points)
Specify any test infrastructure needed (mock audio session, synthetic PCM buffer factory, snapshot testing library)
Specify the test file name and target membership (unit test target vs UI test target, per platform)
Flag any tests that require a physical device rather than simulator

Organize the implementation plan as a prioritized backlog: implement foundational unit tests first (DSP layer, trigger logic, averaging), then view model state tests, then UI smoke tests last.

PART 3 — IMPLEMENTATION
Implement the automated tests in priority order from the backlog. For each test file:

Add .accessibilityIdentifier() modifiers to any SwiftUI views that need them for UI tests
Use XCTestExpectation for any async audio stack tests
Use swift-snapshot-testing for chart view snapshot tests if the library is present; otherwise use XCTAttachment screenshots
Inject dependencies via protocol so tests never require a real microphone or audio session
Add inline comments explaining any non-obvious setup or assertion rationale

After each file, pause and confirm before proceeding to the next, so we can review and adjust the approach as we go.
